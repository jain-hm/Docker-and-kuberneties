####################################################  Day-3 :   Docker Swarm ####################################################
## Docker swarm is needed in complex and advanved production grade environment where there are multiple containers running in a large configuration ##
## There can be 1 or more manager nodes but internally they elect ONLY 1 LEADER NODE using RAFT consensus/agreement which executes the command ( executed from either of the manager node). ##
## Quorum : MIN no of nodes which must agree to elect a leader without ambiguity. Formula : lower(N/2)+1. ##
## If 1 manager node : quorum=1, No redundancy in the cluster, manager dies, all containers are orphaned.
## If 2 manager nodes: quorum = 2. Some redundancy but for quorum we need 2 nodes. So even if 1 disconnects/dies, other one cant elect itself as a leader as it needs 2 nodes as per quorum. Hence cluster stays without leader evenwith 1 manager reachable. ##
## If 3 manager nodes: quorum = 2 ( Minimum recommended for production) : Redundancy. If 1 manager disconnects/dies, remaining 2 can still elect a leader among themselves since together they have quorum of 2.
//                                                                                    If 2 manager dies, 1 still active, quorum cant be achieved and cluster in bad state.
## If 4 manager nodes: quorum = 3 (not recommended). 1 manager dies, 3 still active, build quorum and no impact.
//                                                   2 manager dies, 2 still active, quorum cant be achieved and cluster in bad state. 
//                                                   So only 1 failure allowed ( Same as if we had 3 manager nodes, so no benefit of adding 1 extra manager)
## IMPORTANT : Thats why its advised to have minimum 3 manager nodes ( so that we have 1 failure tolerance) and beyond that advised to use odd no of managers.
## We can deploy single service ( 1 or multiple replicas) or multiple services using a STACK file ( mostly similar to a docker compose file). ###

####################################################  Docker System Directory Structure ####################################################

/var/lib/docker/  : This is the main storage location used by Docker on Linux hosts. It contains all data related to Docker, including: Images , Containers,Volumes,Networks,Storage driver files,Layer metadata

* overlay2/ or aufs/   # Depends on storage driver, overlay2 is default. Stores image layers and container writable layers.
   |-- diff/ or upper/ → writable layer (container file changes which are not in original image template)
   |-- lower/ → image layers   ( Layers from image, read only data)
   |-- merged/ → combined view (what container sees as a total combining image template and custom diles/Drirectories)
   |-- work/ → internal operations for copy-on-write ( Files which are in image template but modified by users,template file is not modified, a different version is stored for docker usage).

* containers/ # Contains metadata and log files for each container. 
* image/overlay2 # Stores metadata about downloaded images. Image IDs,Layer relationships, Repositories and tags information.
* volumes/  # Contains data for all named volumes.
* network/  # Stores network configuration and metadata. Information about bridges, overlays, custom networks, IPAM (IP address management).
* tmp/  # Temporary files used during image builds, pulling layers, etc. Automatically cleaned up by Docker.
* builder/ # Holds cache data used when building Docker images with Dockerfile.
* plugins/  # Contains Docker volume, network, or authorization plugins for extending Docker capabilities.

####################################################  Docker Networking  ####################################################
Docker containers don’t get special privileges — they’re just Linux processes managed smartly.
To stop one container from consuming all CPU or memory from host machine, Docker uses cgroups (control groups).

With cgroup v2, all controls are unified in one place — /sys/fs/cgroup/.
$ mount | grep cgroup    # To check which cgroup version host machine is using. 

Output should be something like : cgroup2 on /sys/fs/cgroup type cgroup2 (rw,nosuid,nodev,noexec,relatime,seclabel,nsdelegate,memory_recursiveprot)


When you run a container with limits (--memory, --cpus), Docker writes these limits to files like memory.max and cpu.max.
The Linux kernel continuously monitors and enforces these values — if the container exceeds them, it gets throttled or killed.
docker run -it   --memory="512m" --cpus="1.5"   ubuntu  # Launch an ubuntu container with memory limited to 512MB and max allowed 1.5 CPU cores.

docker inspect <<CONTAINER-ID>> --format 'Memory limit: {{.HostConfig.Memory}}, CPUs: {{.HostConfig.NanoCpus}}'   # To check allowed memory/CPU limits

sudo ls /sys/fs/cgroup/system.slice/ | grep <<CONTAINERID>>   # To show directory with container specific resource limits.
cd /sys/fs/cgroup/system.slice/docker-<<CONTAINER-ID>>   # To switch to container specific directory to view cgroup related files
cat memory.max   # Shows allocated memory in bytes  divide it by 1024 to get memory size in KB , and dive further by 1024 to get memory size in MB.
cat cpu.max  #  50000 → the quota (allowed CPU time in microseconds) 100000 → the period (total available CPU time) so its like 0.5 cpu assigned to us.

docker stat  # To show containers and their real time resource utilization

stress --cpu 10 --timeout 30   # To simulate laod testing requiring 10 cpus, container
stress --vm 1 --vm-bytes 300M --timeout 20s   # To do dummy load teting inside container for 300MB memory 
stress --vm 4 --vm-bytes 300M --timeout 20s   # To do dummy load teting inside container for 300MB memory  x 4 times parallel ( --vm 4)
stress --cpu 200 --vm 2 --vm-bytes 200M --timeout 30s   # combine CPU and Memory stress testing in 1 command.


cat /sys/fs/cgroup/memory.events   # To heck inside container how many times OOM Occured.
/sys/fs/cgroup/system.slice/docker-<<CONTAINER-ID>>.scope]$ watch -n 1 cat  memory.events   # watch it live on host machine
